Repository architecture

Smart Attendance System

A browser-based attendance web app deployed on Render, with authenticated workflows for enrolling people, processing browser camera frames, recording daily attendance, reviewing history, and exporting reports. A separate PyQt desktop app remains available for local-only use.

Flask + Gunicorn web application Render PostgreSQL persistence Browser camera + OpenCV API CSRF-protected admin sessions Separate PyQt desktop app
Application

Flask + Jinja

web_app.py exposes server-rendered pages and authenticated JSON endpoints; static JavaScript drives browser camera workflows.

Runtime

Render web service

Gunicorn serves Flask on Render's injected PORT; authenticated sessions protect app pages and camera APIs.

Persistence

PostgreSQL

SQLAlchemy stores people, face descriptors, and one attendance row per person and day. Alembic migrations run on startup.

Camera & reports

Browser camera + XLSX

Frames are uploaded for transient OpenCV processing; reports are generated server-side and downloaded by the browser.

02 / Runtime behavior

Main request and data flows

Follow how browser actions are authenticated, processed by the server, and persisted or returned to the browser.

Live recognition → daily attendance

The browser captures frames only after camera permission is granted. JPEGs are processed transiently; a first sighting inserts the daily row and repeated sightings update last_seen no more than once per 15 seconds.

  1. 01 / PERMISSIONEnable cameraThe browser requests explicit camera access using getUserMedia.
  2. 02 / CAPTURESend JPEG framesFrames are posted over HTTPS to the authenticated Flask API and never written to disk.
  3. 03 / DETECTFind a faceOpenCV Haar detection and the configured descriptor backend run in request memory.
  4. 04 / MATCHCompare descriptorsThe closest stored descriptor is accepted only within its backend-specific threshold.
  5. 05 / RECORDWrite daily attendancePostgreSQL enforces one row per person and day; repeat sightings are throttled.

Registration → reusable face template

Enrollment requires explicit consent and several browser camera samples. The application averages the descriptors and stores only that mean descriptor, not the source frames.

  1. 01 / CONSENTConfirm enrollmentThe operator confirms permission before opening the browser camera.
  2. 02 / SAMPLECapture 3–6 framesEach frame is sent to the API and processed without persisting the image.
  3. 03 / AGGREGATEAverage descriptorsNumPy computes one mean descriptor from the valid face samples.
  4. 04 / PERSISTSave the personSQLAlchemy stores the person ID, name, and descriptor in PostgreSQL.
  5. 05 / REFRESHUpdate the directoryThe browser refreshes the people list after the API confirms enrollment.

PostgreSQL attendance → review and spreadsheet

Analytics and reports query attendance rows for the chosen dates. The export route builds an XLSX workbook in memory and streams it as a download.

  1. 01 / READFetch attendanceSQLAlchemy filters attendance by the requested date range.
  2. 02 / SUMMARIZECompute metricsThe analytics route derives totals and per-person attendance activity.
  3. 03 / PRESENTRender resultsJinja templates display attendance and analytics in the authenticated workspace.
  4. 04 / EXPORTBuild workbookOpenpyxl writes the selected range to an in-memory XLSX stream.
  5. 05 / DOWNLOADReturn fileThe browser receives the report as a direct download.

04 / Runtime profile

Technology stack & external dependencies

The Render-hosted web application is the primary attendance workflow. The PyQt application remains a separate local option and retains its own SQLite data.

Web application
Flask, Jinja templates, session authentication, CSRF protection, and JSON API routes in webapp/.
Render runtime
Gunicorn binds to Render's dynamic PORT; /health verifies database availability.
Camera & vision
Browser getUserMedia sends JPEG frames to authenticated API endpoints. OpenCV Haar detection and NumPy descriptors process frames transiently in memory.
Recognition limits
The configured fallback is a deterministic 32×32 grayscale pixel descriptor, which is not reliable production-grade biometric recognition. Liveness / anti-spoofing is not enabled.
Hosted storage
Flask-SQLAlchemy stores user records, face descriptor BLOBs, and daily attendance in PostgreSQL; Alembic migrations are tracked under migrations/.
Reports
Openpyxl creates date-filtered Excel downloads. The browser receives the workbook directly; reports are not stored on the service filesystem.
Local desktop
attendance_system_with_blink.py remains a PyQt program with its own local SQLite database, student classes, live camera workflow, and daily class-wise Excel attendance workbooks under Attendance_records/. It is not connected to the hosted PostgreSQL database.
Desktop attendance workbook
Each recognized student is stored once in Attendance_records/DD-MM-YYYY.xlsx. Worksheets are grouped by class and contain name, roll number, class, and first attendance time.
Environment
requirements.txt covers the web app. Secrets and local connection settings are documented by .env.example and the checked-in .gitignore.
Web runtime

Production entry point

web_app.py exports the Flask WSGI application; Render applies flask db upgrade before starting Gunicorn.

Local runtime

Desktop entry point

run_attendance.py launches the local PyQt app with Add new student and Take attendance actions. Recognition stores one daily row per student in the matching class worksheet in Attendance_records/DD-MM-YYYY.xlsx.

05 / Runtime boundary

Deployment & data architecture

The browser uses its own camera after explicit permission. Frames travel to the Flask service for in-memory processing; persistent application data lives in the attached Render PostgreSQL database.

Deployment

Render Blueprint

Connect this repository as a Blueprint. Render reads render.yaml, installs requirements.txt, sets PORT, and starts Gunicorn after applying migrations.

Database

Render PostgreSQL

DATABASE_URL comes from the linked database. The current Blueprint selects the free plan, which is temporary; upgrade for long-term persistent records.

Legacy desktop

Independent local runtime

python run_attendance.py still launches the PyQt app. Its SQLite database and biometric records are intentionally not transferred to Render.

Open the project README ↗
Before production use: the web app uses one environment-configured administrator and a simple session gate, not user accounts or role-based access. Face descriptors are sensitive and do not receive application-level encryption. Add strong access controls, consent/retention policies, and a security review before real biometric use.
Recognition limits: the deployed base configuration uses a 32×32 pixel descriptor and does not enable liveness detection. It is a demonstration workflow, not reliable biometric authentication or anti-spoofing.
Data semantics: a PostgreSQL unique constraint enforces one attendance row per student and date; repeat recognition refreshes last_seen. The hosted database is separate from the workstation SQLite file. Camera frame bytes are processed in request memory and are not persisted.
Database tables and relationships

users(student_id PK, name, embedding BLOB) stores the registered identity and mean descriptor. attendance(id PK, student_id, attendance_date, first_seen, last_seen) stores daily events, references users with cascade deletion, and enforces a unique student/date pair. Flask-Migrate applies schema revisions.

Recognition backend compatibility

The hosted web application uses a 1024-D grayscale pixel descriptor and a fixed distance threshold. These descriptors are a demonstration fallback, not reliable identity verification.

Request and camera lifecycle

The browser owns camera access and sends bounded JPEG requests to Flask. OpenCV decodes and processes each image in request memory; the service persists descriptors and attendance through SQLAlchemy. Leaving the page or stopping the camera releases the browser media stream.
